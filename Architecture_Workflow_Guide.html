2. JWT Authentication & SSO Bridging Pattern

In a modern microservices or decoupled environment, web clients use cookie authentication for secure browser session handling, while APIs require stateless JWT (JSON Web Tokens) Bearer authentication for cross-service authorization.

2.1 JWT Generation in Lab789AuthServer

When an employee logs in or when the client requests a token via email, the AuthServer encodes user identity, unique identifier (sub), email, and security roles into standard claims signed using HmacSha256:

Lab789AuthServer/Controllers/AuthController.cs C# (.NET 10) 
[HttpGet("token-by-email")]
public async Task<IActionResult> GetTokenByEmail([FromQuery] string email)
{
    var user = await _userManager.FindByEmailAsync(email);
    if (user == null) return NotFound(new { message = "User not found" });

    var roles = await _userManager.GetRolesAsync(user);
    var claims = new List<Claim>
    {
        new Claim(ClaimTypes.NameIdentifier, user.Id),
        new Claim(ClaimTypes.Name, user.UserName ?? user.Email!),
        new Claim(ClaimTypes.Email, user.Email!)
    };
    foreach (var role in roles)
    {
        claims.Add(new Claim(ClaimTypes.Role, role));
    }

    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    var expires = DateTime.UtcNow.AddMinutes(1440); // 24 Hours TTL

    var token = new JwtSecurityToken(
        issuer: _config["Jwt:Issuer"],
        audience: _config["Jwt:Audience"],
        claims: claims,
        expires: expires,
        signingCredentials: creds
    );

    return Ok(new { token = new JwtSecurityTokenHandler().WriteToken(token) });
}
2.2 Preventing Stale Session Token Cross-Contamination
Root Cause of the Account Mismatch Bug: When an administrator or manager switches to an employee account via SSO, the browser's SSO Cookie updates to the new identity, but the ASP.NET Core session cache on the client port (:5133) retained the previous manager's JWT token. Sending the manager's JWT to create an employee transfer request caused a 404: Employee information not found error because manager accounts exist only in AspNetUsers, not in Employees.

The Solution: We implement user-bound token synchronization (JWT_TOKEN_USER). Whenever a request is made, the client checks if the session token's owner matches User.Identity.Name. If a mismatch is detected, the stale token is purged, and a fresh JWT is fetched:

Lab789HRWebClient/Controllers/TransferRequestsController.cs C# (.NET 10) 
private async Task<HttpClient> CreateAuthorizedClientAsync()
{
    var client = _httpClientFactory.CreateClient();
    var currentUserEmail = User.FindFirst(ClaimTypes.Email)?.Value 
                           ?? User.FindFirst(ClaimTypes.Name)?.Value 
                           ?? User.Identity?.Name;

    string? token = null;

    if (!string.IsNullOrEmpty(currentUserEmail))
    {
        // Verify if the cached session token belongs to the currently logged in SSO user
        var sessionUser = HttpContext.Session.GetString("JWT_TOKEN_USER");
        if (string.Equals(sessionUser, currentUserEmail, StringComparison.OrdinalIgnoreCase))
        {
            token = HttpContext.Session.GetString("JWT_TOKEN");
        }
        else
        {
            // User changed in SSO! Evict stale token
            HttpContext.Session.Remove("JWT_TOKEN");
            HttpContext.Session.Remove("JWT_TOKEN_USER");
        }

        if (string.IsNullOrEmpty(token) && User.Identity?.IsAuthenticated == true)
        {
            // Fetch fresh JWT for current identity
            var authClient = _httpClientFactory.CreateClient();
            var tokenResp = await authClient.GetAsync($"{_authServerUrl}/api/Auth/token-by-email?email={Uri.EscapeDataString(currentUserEmail)}");
            if (tokenResp.IsSuccessStatusCode)
            {
                var json = await tokenResp.Content.ReadAsStringAsync();
                using var doc = JsonDocument.Parse(json);
                if (doc.RootElement.TryGetProperty("token", out var tokenEl))
                {
                    token = tokenEl.GetString();
                    HttpContext.Session.SetString("JWT_TOKEN", token!);
                    HttpContext.Session.SetString("JWT_TOKEN_USER", currentUserEmail);
                }
            }
        }
    }

    if (!string.IsNullOrEmpty(token))
    {
        client.DefaultRequestHeaders.Authorization = new AuthenticationHeaderValue("Bearer", token);
    }
    return client;
}

3. Redis Distributed Caching Architecture

To minimize database I/O and optimize throughput for frequent employee lookups, Lab789HRWebAPI leverages the Cache-Aside (Lazy-Loading) pattern integrated with proactive cache invalidation upon any data mutation.

A Cache-Aside Read Flow
  1. Client sends GET /api/Employees with JWT Bearer Token.
  2. Controller queries Redis key: Lab789HR_employees_list.
  3. Cache Hit: Data returned instantly from memory in < 2ms.
  4. Cache Miss: SQL Server queried, result stored in Redis with 10-minute TTL, then returned to caller.
B Cache Invalidation (Eviction)
  1. New employee created (POST /api/Employees) OR transfer request approved (PUT /api/TransferRequests/{id}/review).
  2. Database records updated within transaction.
  3. Controller immediately invokes _cache.RemoveAsync("employees_list").
  4. Subsequent read hits database and repopulates fresh cache automatically.
3.1 Cache-Aside Implementation in Controller
Lab789HRWebAPI/Controllers/EmployeesController.cs C# (.NET 10) 
private const string EmployeesCacheKey = "employees_list";

[HttpGet]
public async Task<ActionResult<IEnumerable<Employee>>> GetAll()
{
    // 1. Check Redis Cache
    var cachedData = await _cache.GetStringAsync(EmployeesCacheKey);
    if (!string.IsNullOrEmpty(cachedData))
    {
        var cachedEmployees = JsonSerializer.Deserialize<List<Employee>>(cachedData);
        return Ok(cachedEmployees);
    }

    // 2. Cache Miss: Query Database
    var response = await context.Employees.AsNoTracking()
                                          .OrderByDescending(e => e.Salary)
                                          .ToListAsync();

    // 3. Store in Redis with a 10-Minute Sliding / Absolute TTL
    var options = new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
    };
    await _cache.SetStringAsync(EmployeesCacheKey, JsonSerializer.Serialize(response), options);

    return Ok(response);
}

4. Department & Position Transfer Workflow

The department transfer module allows employees to submit formal transfer requests to target departments and specific positions. Managers review, approve, or reject these requests with atomic database updates and instant cache synchronization.

1 Dynamic Form Pre-Loading: When an employee navigates to /TransferRequests/Create, the system queries their current profile via GET /api/Employees/by-email/{email}. It displays a summary card showing their full name, email, current department, and current position.
2 Interactive Position Mapping (JavaScript): When the employee picks a target department, client-side JavaScript dynamically populates the position dropdown with valid titles specific to that department (e.g., IT → DevOps Engineer, Senior Developer; Marketing → SEO Specialist, Content Creator).
3 Atomic Database Transaction & Cache Invalidation: When a Manager approves a request on /TransferRequests/Pending, the API executes an Entity Framework database transaction. It updates the request status to APPROVED, updates the employee's Department and Position in the Employees table, commits the transaction, and evicts the Redis cache.
4.1 Transactional Approval & Atomic State Mutation
Lab789HRWebAPI/Controllers/TransferRequestsController.cs C# (.NET 10) 
[HttpPut("{id}/review")]
[Authorize(Roles = "Manager,Admin")]
public async Task<IActionResult> ReviewRequest(int id, [FromBody] ReviewTransferRequestDto dto)
{
    var reviewerEmail = User.FindFirstValue(ClaimTypes.Email) ?? User.FindFirstValue(ClaimTypes.Name);

    // Use an explicit transaction to ensure both request status and employee profile mutate atomically
    using var transaction = await _context.Database.BeginTransactionAsync();
    try
    {
        var request = await _context.DepartmentTransferRequests.FindAsync(id);
        if (request == null) return NotFound(new { message = "Transfer request not found" });
        if (request.Status != "PENDING") return BadRequest(new { message = "This request has already been processed" });

        request.ReviewerEmail = reviewerEmail;
        request.ReviewNote = dto.ReviewNote;
        request.ReviewedAt = DateTime.UtcNow;

        if (dto.IsApproved)
        {
            request.Status = "APPROVED";

            // Mutate Department and Position on the Employee entity
            var employee = await _context.Employees.FindAsync(request.EmployeeId);
            if (employee != null)
            {
                employee.Department = request.ToDepartment;
                employee.Position = !string.IsNullOrEmpty(dto.ApprovedPosition)
                    ? dto.ApprovedPosition.Trim()
                    : request.ToPosition.Trim();

                _context.Employees.Update(employee);
            }
        }
        else
        {
            request.Status = "REJECTED";
        }

        await _context.SaveChangesAsync();
        await transaction.CommitAsync();

        // Evict Redis cache upon approval so all clients immediately see updated department and position
        if (dto.IsApproved)
        {
            await _cache.RemoveAsync(EmployeesCacheKey);
        }

        return Ok(new { message = dto.IsApproved ? "Department transfer approved successfully" : "Transfer request rejected", request });
    }
    catch (Exception ex)
    {
        await transaction.RollbackAsync();
        return StatusCode(500, new { message = "Error processing transfer request", error = ex.Message });
    }
}
